# SaaS 教材与操作文档编写标准

本标准用于把零散页面说明组织成可供新成员独立学习的资料。它记录长期有效的结构、写作、证据和事实核对规则，不记录某次编写任务的进度或聊天历史。

## 一、资料库结构

### 三个学习维度

资料库顶层使用三个无序号目录：

1. **操作手册**：回答进入哪个端、打开哪个菜单、点击什么、看到什么结果。
2. **部署运维**：回答安装拓扑、启动参数、网络、升级、备份、监控和故障处理。
3. **产品设计**：回答对象为何存在、由谁维护、何时产生、怎样关联及权限如何生效。

这三个目录表示问题维度，不表示互斥读者。普通用户、实施人员、运维人员和开发人员可以按任务跨目录阅读。每个功能都要在学习索引中连接适用维度；某一维度确实不适用时，应说明边界，不能创建空文档凑数。

每篇文档顶部的 **推荐优先学习** 或 **相关学习** 使用纵向无序列表展示，每个链接或“不适用”说明单独一项。禁止使用 `·`、竖线或连续文本把多个入口横向拼成一行。

### 产品设计的知识图谱与阅读顺序

创建、整理或新增产品设计文档时，必须根据知识图谱逐层分析前后置功能关系，再列出阅读顺序，不能只按文件名、创建时间或主题名称平铺目录。

1. 先读正文，识别每篇涉及的概念、业务对象、维护角色、输入条件和输出结果。每条前后置关系都要说明“下游需要上游提供什么”，不能仅凭文档互相引用判断依赖。
2. 区分两种关系：知识前置说明理解当前专题需要哪些概念；业务前置说明执行当前功能需要哪些真实对象、权限或生效状态。阅读完成不等于业务条件已经具备。
3. 按依赖逐层排列，保证前置文档先于依赖它的文档。概念与边界、身份与能力供给、权益交付、权限生效、具体应用可作为分层参考，实际层级由当前内容决定，不固定套用篇数和顺序。
4. 在产品设计索引中提供带关系含义的知识图谱，以及包含“推荐顺序、知识层、文档链接、直接前置、后续功能或用途”的阅读表。同层独立分支可分别学习；推荐通读顺序不能被写成业务必须逐项执行的流程。
5. 遇到循环先辨明原因：概览中预告后续专题，可明确先读概览再展开；业务中的续费、扩容或异常恢复属于反馈关系，单独说明，不作为首次阅读的反向前置。无法解释的真实依赖矛盾应标明待核实，不能强行编造顺序。
6. 新增或调整文档时同步更新同一索引与依赖图，沿用资料库命名约定，不为排序擅自批量改名。交付前核对正文依据、图表关系一致性、文档覆盖、前置顺序无循环，以及文档与图片链接可达。

### 操作手册层级

1. 先按产品实际系统边界划分，并从当前代码和部署配置确认各系统的数据归属、数据库边界和同步方式；不要默认共库或分库。JetLinks 的已确认边界见 [jetlinks-product-boundaries.md](jetlinks-product-boundaries.md)。
2. 再按真实用户身份划分。角色目录中的菜单名称、布局和操作必须来自该角色实际页面，不能给不同角色复制相同目录。
3. 按当前产品实际存在的层级组织对象，并解释各层如何产生和下沉权限。JetLinks 的平台、项目、项目应用三级边界和应用对象区分见 [jetlinks-product-boundaries.md](jetlinks-product-boundaries.md)。
4. 顶级系统目录提供名词说明。名词使用 Markdown 表格，术语用标准 `**加粗**`，禁止在表格中插入 HTML 只为实现样式。
5. 一个目录只有一篇正文且没有独立导航价值时，取消该目录，直接让目录名成为文档名。不要制造只有 `README.md` 和一篇正文的空层级。
6. 工作台、仪表盘或汇总页的多个卡片和空态通常合并为一篇文档；只有某个子视图具备独立任务、决策或交接结果时才拆分。

### 菜单与文档颗粒度

1. 每个真实子菜单先作为一个候选文档，因为它通常代表不同功能入口。
2. 如果一个子菜单只有低信息量的增删改查，并且其记录只供相邻功能组合使用，应与消费它的功能合并。例如服务、规格与区域共同形成可订阅能力时，写成一篇综合文档。
3. 不要为“打开列表、新增、编辑、删除”单独发布教材。独立文档必须有明确业务结果、关键选择、权限边界、上下游关系或恢复路径。
4. 综合功能要引用上游准备文档和下游消费文档，让读者知道当前输出交给谁、在哪里继续。
5. 目录顺序遵循用户已确认的角色工作顺序，不能按作者理解自行重排；每个菜单内部再按依赖顺序排列。JetLinks 的已确认顺序见 [jetlinks-product-boundaries.md](jetlinks-product-boundaries.md)。

### 大纲与骨架模式

用户要求先建立可手写的大纲时，不扩写成未经验证的完整教材，但每篇骨架仍必须包含：

1. 约 50–80 个中文字符的功能概述。
2. 真实端、菜单、子菜单和按钮入口。
3. 使用有序列表表达的前置条件和基础操作顺序。
4. 上游对象来源、下游消费入口及可点击链接。
5. 当前代码或界面仍未核实的字段、权限或状态，并明确标为待核实。

只有标题列表不算可用大纲。大纲没有真实截图时必须称为骨架，不能称为已经完成的培训教材。

## 二、从零到一的任务链

### 零数据起点

默认数据可能为零。每个汇总页、选择器和列表都要说明：

1. 空数据是否正常。
2. 第一条数据由谁创建。
3. 应进入哪个端、菜单和功能创建。
4. 创建完成后回到当前流程的哪一步。
5. 有数据时如何继续，不要只写空态，也不要用已有数据截图冒充空态。

“没有项目”“没有可选区域”“没有服务规格”“没有网关”“没有角色或菜单权限”都是独立分支，不能只写“联系管理员”。

### 对象与角色来源

任何角色、身份、关系、权限、状态或业务对象第一次进入任务链时，必须定义或链接介绍文档，并回答：

1. 它由哪个系统和菜单创建。
2. 谁可以创建或分配。
3. 哪次保存后它才开始存在。
4. 它控制什么，不控制什么。
5. 下游在哪个页面消费或验证。

教材称谓与产品模型不一致时，要立即说明映射。例如“项目负责人”如果实际来自项目所有者字段，就必须说明项目创建或指定所有者后才产生，不能把它写成用户创建时已有的固定角色。

### 线性闭环

基础课程按以下逻辑组织，而不是按概念堆叠：

1. 准备下一角色需要的最小账号和平台能力。
2. 创建业务对象并明确所有者。
3. 开通对象运行所需的服务或配置。
4. 建立用户与项目或应用的关系。
5. 配置菜单、按钮和资产权限。
6. 切换到接收角色验证可见入口、可执行动作和数据范围。
7. 进入真实业务功能完成一个可观察结果。

每一步的输出必须成为下一步的输入。项目、负责人、管理员、成员、角色、菜单权限或资产权限不能在中途凭空出现。

## 三、单篇操作文档结构

### 固定标题

普通任务文档依次使用：

```markdown
## 简单概述
## 前置条件
## 操作步骤
## 结果验证
## 注意事项
```

上游配置只有被下游功能消费后才有意义时，必须用 `## 后续功能` 替换 `## 结果验证` 和 `## 注意事项`。后续功能必须使用有序列表，逐项链接接收文档并说明交接对象和范围变化。

### 简单概述

1. 默认控制在约 50–80 个中文字符，可用一到两句。
2. 只说明本篇介绍哪个角色、哪个菜单、什么操作和什么结果。
3. 不写平台价值、营销表达、宽泛背景或“帮助用户更好地”等空话。
4. “培训”是材料用途，不是项目类型。禁止自行命名“培训项目”“科教项目”等产品中不存在的对象。

### 前置条件

1. 必须使用有序列表。
2. 第一项从学习者当前操作位置出发，说明已登录哪个端以及需要的角色或权限。
3. 只列真实上游输出、必要硬件和本次操作必须掌握的概念。
4. 涉及其他文档的条件必须加链接，链接到实际创建或配置该对象的文档。
5. 不把当前文档要创建的结果写成前置条件。
6. 不写本地测试地址、账号密码、令牌或只适用于某台机器的 IP。培训材料应适用于官方 SaaS 和用户自行部署的服务。
7. 已由平台默认提供、部署人员必然知道或当前用户无需处理的事实不要列入操作前置条件。
8. 操作依赖部署参数或产品概念时，引用部署运维或产品设计文档，只写当前操作需要接收的结果。
9. 概念认知类条件先说明学习者应了解的对象关系；不了解时再推荐阅读对应文档。除非阅读本身是可验证的必要动作，不得写成“已阅读某文档”的强制前置条件。

### 操作步骤

1. 必须使用有序列表。
2. 第一步采用“登录 **SaaS 运营端/Runtime 项目端**，进入 **菜单 > 子菜单** 下的 **功能**”形式，明确端、菜单和入口。
3. 一级步骤摘要只表达一个任务目标，控制在约 50 个中文字符，并说明操作位置、主要动作或配置内容以及预期即时结果。
4. 一级摘要下使用缩进的二级有序列表，逐项说明具体点击位置、关键选择、字段组、提交动作和即时结果；简单且信息完整的单层操作可以短于 50 字。
5. 约 50 字只约束一级步骤摘要的可读性和信息量，不是内容上限。复杂任务必须在二级有序列表中保留所有必要点击、关键选择、字段组、提交动作和即时结果，禁止压缩成“配置后保存”等空泛句子。
6. 引用块、截图、图注和表格不计入一级步骤长度，不得为了满足字数而机械拆分这些辅助内容。
7. 按页面可见顺序写操作，不按代码实现顺序或概念分类写。
8. 每个非简单步骤说明操作前可见状态、点击位置、必要输入或选择规则、保存动作以及立即可见结果。
9. 复杂表单按用户决策拆步；不能用“点击新增，填写信息并保存”代替真实操作。
10. 只列当前 UI 真正必填的字段，以及会改变下游结果的可选字段。必填状态以当前表单校验和提交逻辑为准。
11. 不使用“先确认是否可复用”“按需选择”“确保配置正确”等没有入口、判断标准和下一动作的句子。
12. 字段设计理念、依赖关系和数据来源放在字段首次出现后的引用块中，不把没有独立操作的说明编号成主步骤。
13. 同一表单内无需独立判断的简单填写可以合并；价格规则、资源配额、权限授权、跨角色交接和失败恢复必须保留完整操作并独立成步。
14. 一个步骤需要对比或解释多个重要参数时，使用 Markdown 表格列出参数、填写要求、示例值或选择规则，不在段落中连续堆叠决策信息。
15. 参数名、参数值、配置键、命令、URL、媒体地址和文字中出现的文件路径使用行内代码格式，例如 `access-id`、`https://runtime.example.com`、`assets/example.png`。
16. 菜单和按钮继续使用加粗格式；需要点击或渲染的 Markdown 链接、图片语法保持原格式，只对作为说明文字展示的地址或路径使用行内代码。
17. 连续且简单的动作应合并为一句，例如“进入页面并点击新增”，不得为了满足字数或层级形式机械拆分。
18. 页面显示内容、空数据含义、字段原理、默认值和结果解释不属于操作动作，应放入引用块、参数表、图注或验证章节，不得编号成操作步骤。
19. 普通名称、普通编码等字段只有“必填”或“填写展示值”信息时，直接写入操作句，不单独制作参数表。仅对影响安全、路由、权限、价格、配额、生命周期或下游结果的参数补充说明。
20. 本节格式适用于全部操作手册，不限于示例文档或重点功能。普通列表展示字段、已有查询条件和不影响后续动作的常规空列表说明直接省略。
21. 只有空态或页面状态会改变下一动作、暴露缺失前置条件或提供恢复入口时才保留，并放入说明块或注意事项，不编号为操作。
22. 表格必须帮助学习者比较方案、选择重要参数、追溯数据来源或理解关键边界。单元格只重复“必填”“展示名称”“可以修改”“只读”等页面常识时，删除表格，把操作合并为一句，只保留影响结果的例外说明。
23. 学习索引、名词对比、对象关系、部署参数和经过核实的方案对比表不属于低密度参数表，不得因本规则机械删除。

### 结果验证与注意事项

1. 结果验证写明验证角色、菜单入口、目标对象、预期状态或关系，以及失败后返回哪篇文档。
2. “保存成功”“页面有数据”不能单独作为最终验证；要检查能被下游角色消费的持久结果。
3. 注意事项只保留影响结果的分支和错误，按“现象 → 原因 → 处理 → 再验证”写。
4. 当前页面没有入口的能力要明确边界，不能根据后端枚举或接口推测为用户可操作功能。

### 复合可用条件

“启用”“可用”“已连接”“已发布”“订阅有效”等状态可能共同决定对象是否可选或可用。写作前要核对 UI 过滤、后端查询条件、关联对象和连接状态，完整列出必要条件。禁止把复合条件缩写成“启用后即可使用”。

## 四、字段与产品事实

### 字段范围

基础教程以最小有效输入完成闭环。可选的说明、图标、标签、排序、备注和高级参数默认省略；只有它会改变本任务结果或某个分支时才写。

### 非用户输入字段

选择器、树、只读字段、系统 ID、状态、默认值、计算值和自动同步数据第一次出现时，要探查并说明：

1. 数据来自哪个系统、菜单、接口或系统内置规则。
2. 为什么当前功能要引用它。
3. 用户是否可以在当前页面修改。
4. 数据缺失或错误时去哪里修复。

系统内置功能要说明这是产品设计；引用其他功能的数据要链接其维护入口；跨系统查询要说明同步时点和读写边界。不得只写“自动生成”“自动带出”。

### 关系与设计结论

一对一、一对多、跨环境复用、角色映射、菜单交集和资产隔离等结论必须同时核对当前实体、约束、接口和 UI。证据不一致时标为未验证，不能凭字段名推断。

必须区分相似对象，例如：

- SaaS 可订阅服务与 Runtime 微服务进程。
- 实体网关与 Runtime 设备接入网关。
- SaaS 应用方案、Runtime 项目应用、项目应用模板与应用中心资源。
- SaaS 平台角色、项目所有者或成员关系、Runtime 角色与应用角色。
- SaaS 控制面数据库、Runtime 业务数据库，以及同一 Runtime 内按项目或租户进行的逻辑隔离。

### 地址与部署示例

当前本地环境的 `IP:端口` 只能作为示例，不能写成固定产品规则。若产品支持域名、HTTPS、反向代理、项目编码占位符或多种路径模板，应分别说明：

1. 本地部署示例值。
2. 域名或 HTTPS 的通用写法。
3. 占位符由谁替换以及替换时点。
4. DNS、证书和反向代理属于部署运维，不由操作页面自动完成。

标准教材的前置条件不得出现当前机器的固定地址；需要演示时放入明确标注的示例表或部署文档。

## 五、截图与证据

### 先做步骤证据表

写正文前先列出每个步骤需要的证据。以下情况必须有独立的真实 Chrome 截图：

1. 不熟悉的菜单入口或空态。
2. 复杂表单和关键业务选择。
3. 菜单、按钮或资产授权。
4. 跨角色交接后的接收结果。
5. 阻断错误、恢复入口和恢复结果。
6. 最终可持久验证的业务结果。

简单、连续、确定性的两字段新增或价格、周期、额度填写可以不截图，但正文必须足够明确，并由后续持久结果证明。

### 截图规则

1. 使用真实 Chrome 页面和当前功能对应的真实账号。
   - 在已经授权的本地或培训环境中，编写者应通过真实用户管理、角色管理和成员关系入口自行创建测试账号并完成登录，不把常规账号准备交还给用户。
2. 不同角色分别登录和截图，不能共用一张管理员截图证明其他角色的页面。
3. 一张图只证明它真实显示的页面、角色和状态；删除错误截图不能代替补拍正确截图。
4. 每张图紧跟对应步骤，编号与步骤一致。关键步骤不能只在文末放一张总图。
5. 图片说明使用“图 N（步骤 N）：角色在页面处于何种状态；可证明什么”的形式。
6. 已有数据截图只能证明有数据状态，不能证明首次进入的空态。
7. 密码、访问密钥、设备凭证、支付信息和客户数据必须遮蔽。
8. 无法取得目标角色、设备或真实页面时，将文档标记为未完成并记录阻塞，不能复用旧图、模拟图或其他角色截图。

## 六、交付前检查

1. 从零数据状态按文档完整走一遍，确认没有依赖讲师口头补充的概念或步骤。
2. 检查每个角色和业务对象的来源、拥有者、产生时点、消费入口和验证入口。
3. 检查目录颗粒度：低信息 CRUD 已合并，独立任务没有被错误合并，单文档空目录已压缩。
4. 检查所有菜单名、按钮、字段必填规则、状态和权限均来自当前 UI 与代码。
5. 检查截图角色、页面、状态和声明一一对应。
6. 检查所有 Markdown 链接、图片路径和跨三个维度的引用可达。
7. 检查概述长度及标题结构：普通任务文档使用五个固定标题；上游交接文档使用四个标题，末尾为 `后续功能`。两种文档的前置条件与操作步骤都必须使用有序列表；复杂操作的一级摘要约 50 字并说明位置、动作和即时结果，二级有序列表保留完整操作；多个重要参数需要比较时使用表格，普通字段不机械制表，参数和文字中的地址、路径使用行内代码。
8. 任何核心链路缺少真实证据、对象来源或接收角色验证时，只能交付为待完善骨架，不能称为完成的培训教材。
